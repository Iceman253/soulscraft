---

A browser-based GM and player tool for the **Soulscraft 3.1e** tabletop RPG — a Minecraft-flavoured 2d6 system. Runs entirely in the browser with no backend; all data is stored in `localStorage`.

---

## What It Does

### Campaign Management
Create and switch between multiple campaigns. Each campaign is fully isolated — its own map, characters, quests, and log. Campaigns can be exported as JSON and re-imported, making it easy to back up or share a session.

### World Map
An interactive node-graph canvas (powered by [React Flow](https://reactflow.dev/)) where you place **area nodes** — settlements, dungeons, wilderness regions, portals, and more — and connect them with travel edges. Each edge can be tagged as Safe, Risky, or Deadly, and a label can describe the journey (e.g. *"3 days north by sea"*).

- **Fog of war** — areas can be hidden until the GM reveals them
- **Player visibility** — the GM controls which areas are shown to players separately from fog
- **Custom map background** — upload any image to sit behind the canvas
- **Sub-maps** — double-click any area to open a nested canvas inside it, with its own nodes and connections (e.g. the rooms of a dungeon). Sub-maps are infinitely nestable.
- **Character tokens** — characters placed in an area appear as portrait tokens on its node

### Character Sheets
Full rulebook-accurate sheets for PCs and NPCs, organised into tabs:

| Tab | Contents |
|-----|----------|
| **Stats** | Portrait, species, class, level, XP bar, HP, Stamina Dice, armor loadout (auto-DEF), weapon loadout (damage bonus), location |
| **Class** | Class-specific per-rest resources (Warrior maneuvers, Hunter prey, Vindicator voices, Enchanter tome, Delver evasions, Wildspeaker tethers, Evoker wards/vex/fangs, Tecton craft charges, Alchemist essences), plus discipline edge toggle |
| **Skills & Traits** | Passive roll bonuses and species/personal traits |
| **Abilities** | Active SD-cost powers with material costs |
| **Inventory** | On-hand block meter (≤10 blocks), storage at each place, the character's Ender Chest, currency (copper/iron/gold/emerald/diamond), rations |
| **Effects** | Active potions/conditions with scene or day timers, gear enchantments |

**Armor** uses a slot-based system (helmet, chestplate, leggings, boots, shield) with per-material DEF values derived from Minecraft proportions. Total DEF is always auto-calculated. Individual pieces can be overridden to represent damage or enchantment.

**Weapons** work similarly — type + material determines a base damage bonus that adds to the character's class damage die.

### Combat Tracker
Full-screen overlay showing the initiative order. Each row has the combatant's name, HP bar, DEF, active effect badges, and action buttons. The GM can roll attacks and defenses, adjust HP, and advance turns. When combat is active, the Player View (see below) automatically switches to a filtered combat display.

### Dice Roller
Animated 2d6 roller with:
- SD Boost (spend a Stamina Die for a reroll)
- **Difficult Action mode** — three sequential rolls where 2+ successes = success overall
- Double-6 detection with a prompt to award XP

### Rest System
Log a rest with a checklist of conditions (fed, shelter, safe, calm mind). Full conditions = Good Rest (full HP + SD recovery); partial = Poor Rest (half recovery). Missed rests accumulate a d4 penalty per skip, shown as a badge on character cards.

### Other Features
- **Quest Tracker** — active/completed/failed quests with per-objective checkboxes and linked area
- **Bestiary** — rulebook creatures plus GM custom entries; "Add to Combat" spawns directly into the tracker
- **Items** — world items that can be assigned to areas, sub-nodes, or characters
- **Session Log** — auto-logs every meaningful event (reveals, moves, HP changes, rest, XP, combat end); GM can add manual entries
- **Pinned Notes** — colour-coded sticky notes in the right rail
- **Reference Panel** — searchable potion recipes and enchanting data from the rulebook
- **End Scene / End Day** buttons — automatically tick down scene- and day-duration effects and enchantments across all characters, removing anything that expires

### Player View
A read-only full-screen overlay the GM can flip to for a second monitor or tablet. Shows:
- A clean, non-interactive version of the world map with only player-visible areas
- Traveling markers — when a character is en route to a secret destination, players see a dashed animated path leading to "???" with an optional travel note
- All character stats, HP, effects, and inventory in a read-only panel
- When combat is active: a filtered initiative list (names, HP, whose turn, effects — no DEF values, notes, or roll UI)

### Mining and Building
Players do this on their own device, phone or desktop, and the GM signs off:
- **Go Mining** — pick the place, materials and amount, then roll. The GM sees the result and awards the blocks. A pickaxe mines anything; an axe only gets its full bonus on wood (a shovel on dirt and sand, a hoe on leaves) and is 3 worse on anything else.
- **Mines** — a place type on the main map or in a sub-location. Each character can leave blocks at a mine and pick them up when they're back there.
- **Carrying** — characters carry 10 blocks at most, and anything past that goes into storage where they are. A player can ask the GM for more: the GM sets a temporary limit, which ends once they're carrying fewer than 10 blocks.
- **Storage** — chests stay where they're left (p.7), so storage belongs to a place (an area or sub-location). A character can use the storage where they are and in the places around it; the rest is listed as elsewhere. Mined blocks stay where they were mined unless carried. Things left with no place (out on the world map, or at a place that was deleted) can be collected from anywhere, and the GM can move a whole store to the place it really is.
- **Ender Chest** — each character has their own, holding only what was put in it on purpose. It can be opened from anywhere, but only while someone with them (at the same place) carries an Ender Chest. Builds draw blocks from the storage here, then the Ender Chest if it's open, then what's on hand.
- **Start a Build** — draw a 16×16 icon (or start from a shape), say what it's for, pick a size, and place it on the world map or inside any area or sub-location. The GM sees the icon, the description and the spot on the map, and approves it in one tap.
- **Working on a build** — players put in their own blocks and redstone dust directly. Days worked and requests to speed a build up go to the GM.
- **After it's built** — the GM can damage a build (it needs blocks put back in, which players do from its sheet) or destroy it, leaving ruins its builders can rebuild. A finished, undamaged build can be picked as the shelter when logging a rest. Builds by a Tecton show their Prime Order bonus.
- Tap a build on the map for its progress, or tap an area to look inside it. Secret sub-locations stay hidden from players.

## How It Works

### Tech Stack
| Layer | Library |
|-------|---------|
| Build | Vite + TypeScript |
| UI | React 19 |
| State | Zustand (one store per feature module) |
| Canvas | @xyflow/react v12 |
| Styling | Tailwind CSS v4 |
| Icons | lucide-react |
| IDs | `crypto.randomUUID()` |

### Data Storage
Everything lives in `localStorage` under three key types:

```
soulscraft_campaigns          → lightweight index of all campaigns (name, dates, counts)
soulscraft_campaign_{id}      → full JSON blob for one campaign (all game data)
soulscraft_active_campaign    → the currently open campaign ID
soulscraft_mapbg_{id}         → map background image (stored separately so it can be evicted)
img_portrait_{charId}         → character portrait images
img_armor_{material}_{slot}   → armor piece images (shared across all characters)
img_weapon_{material}_{type}  → weapon images (shared across all characters)
```

No server, no accounts, no network requests.

### Store Architecture
Each feature has its own Zustand store with a `hydrate()` action. On campaign switch, `App.tsx` loads the campaign JSON and calls `hydrate()` on every store. Any mutation immediately writes back to localStorage via the campaign store's `updateCampaignData()` action.

### Map & Sub-maps
The world map and every sub-map are React Flow canvases. Nodes are derived from the Zustand store into a memoized `baseNodes` array; a local `rfNodes` state is kept in sync via `useEffect` and updated on every drag via `applyNodeChanges` so movement is smooth without round-tripping the store mid-drag. Position is only persisted to the store when `dragging === false`.

Sub-maps use a path array (e.g. `['areaId', 'subNodeId']`) to navigate and mutate nested nodes inside the area tree without flattening the data model.

## Self-Hosting (Proxmox LXC or any Debian/Ubuntu machine)

Soulscraft is a static React app plus a small Node server (`server/`) that stores
campaigns in SQLite and syncs them live between devices. nginx serves the app over
HTTPS and is the only way in: the Node server listens on `127.0.0.1` only.

### 1. Into a container you already made (recommended)

Create a plain **unprivileged** Debian/Ubuntu LXC (or VM) with ≥1 GB RAM, then run inside it as root:

```bash
bash -c "$(curl -fsSL https://raw.githubusercontent.com/Iceman253/soulscraft/master/deploy/install-native.sh)"
```

This installs nginx and Node, runs the tests, builds the app, serves it over HTTPS
(self-signed certificate: accept the one-time browser warning), and advertises
`<hostname>.local` via mDNS. Re-run `bash /opt/soulscraft/deploy/install-native.sh` to update.

### 2. Proxmox — one command on the host

Run **on the Proxmox VE host** as root. It creates an unprivileged Debian 12 LXC and runs the installer above inside it:

```bash
bash deploy/proxmox-lxc-setup.sh
```

Configurable: `CTID`, `CT_HOSTNAME`, `DISK_GB`, `CORES`, `RAM_MB`, `BRIDGE`, `STORAGE`, `TEMPLATE_STORE`, `REPO_URL`.

> The `Dockerfile` / `docker-compose.yml` / `deploy/install.sh` build the frontend only,
> without the campaign server, so campaigns can't be created or shared with them.

### Security

The installer sets up:

- **Campaign codes** are required to read anything in a campaign (data, images, live
  updates), not just to change it. They're stored as salted scrypt hashes. New codes
  must be at least 6 characters; use something longer than a PIN if the app is reachable
  from the internet.
- **Brute-force limits:** 10 wrong codes per client and 100 per campaign every 15
  minutes, 5 new campaigns per client per hour, at most 50 campaigns, and per-request
  limits in nginx.
- **Home network vs. internet:** requests that arrive through a tunnel on the container
  (Tailscale Funnel/Serve) can't create or import campaigns, and can't open campaigns
  whose code is shorter than 6 characters until the GM changes it.
- **Storage limits:** 4 MB per campaign, 3 MB per image (PNG/JPEG/WebP/GIF only),
  1000 images per campaign, and writes stop when less than 150 MB of disk is free.
- **Sandboxed backend:** runs as the `soulscraft` user under systemd sandboxing and can
  only write `/var/lib/soulscraft`.
- **Daily backups** of the database in `/var/lib/soulscraft/backups` (last 7 kept).
- **Security headers** (Content-Security-Policy and friends) and automatic Debian
  security updates.

**Changing a campaign's code** (there's no screen for it; anyone with the code can
use the app as GM, so change it if it leaks):

```bash
cd /opt/soulscraft/server
runuser -u soulscraft -- env DATA_DIR=/var/lib/soulscraft node set-code.js             # list campaigns
runuser -u soulscraft -- env DATA_DIR=/var/lib/soulscraft node set-code.js "Everworld" # asks for the new code
```

Devices using the old code are sent back to the campaign list and asked for the new one.

**Restoring a backup:** `systemctl stop soulscraft-server`, copy a file from
`/var/lib/soulscraft/backups/` over `/var/lib/soulscraft/soulscraft.db` (delete the
`-wal`/`-shm` files next to it), `chown soulscraft: ` it, and start the service again.

**Putting it on the internet:** use a tunnel that terminates HTTPS with a real
certificate and forwards to `https://localhost:443` on the container, such as
Tailscale Funnel (`tailscale funnel --bg https+insecure://localhost:443`). Anyone can
see the campaign *names*; everything else needs a code.

**Local hostname options:** the installer gives you `<hostname>.local` via mDNS. For a
name that resolves on every device regardless of mDNS support, add an A-record (e.g.
`soulscraft.lan → <container-ip>`) on your router or Pi-hole instead.

## Notes
- Tested in Chrome and Firefox. Safari should work but is untested.
- Needs Safari or iOS 16.4+, Chrome 111+ or Firefox 128+, the minimums for Tailwind CSS 4.
- localStorage has a ~5 MB limit per origin. A size warning appears in the campaign switcher if data approaches this limit. Image uploads are the main culprit; the map background is stored under a separate key so it can be cleared independently.
